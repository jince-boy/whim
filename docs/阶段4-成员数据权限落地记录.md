# 阶段 4：租户成员数据权限落地记录

## 当前资源归属

成员是 `sys_user_tenant` 关系，`tenant_id` 是租户边界，`dept_id` 是该用户在本租户的主部门，`user_id` 是“本人”归属。全局身份表 `sys_user` 不适合直接套用租户拦截器；成员列表通过明确的租户和动作范围查询关联身份摘要。

`system:member:list`、`system:member:status`、`system:member:department` 分别使用实际授予该动作的有效租户角色计算六种数据范围。列表在 SQL 中过滤成员原有主部门或本人；停用和部门调整先核对目标，再在最终写语句中同时限制成员 ID、用户 ID、租户 ID 和原归属范围。部门调整的新部门也必须属于本次动作的全部或部门范围，且其整条祖先链有效。仅本人范围可以管理本人关系，但不能借此把自己分配到任意新部门；清空自身主部门是缩小归属的操作。

角色、角色权限、租户套餐和平台授权仍属于权限配置资源，继续由独立功能权限码与明确的平台或租户作用域保护。它们不使用成员的部门归属代替授权管理权限。

## 动态验收

本地两租户夹具覆盖六种范围的成员列表、当前租户和跨租户目标、范围外同租户目标、新部门校验、状态和主部门写入、本人范围、空主部门与不同动作授权角色，共 **52/52** 项通过，见[成员范围验收明细](阶段4-成员数据权限动态验收明细.json)。最终 SQL 日志确认部门过滤写入 `ut.dept_id IN (...)`，本人过滤写入 `ut.user_id = ...`，写语句同时保留租户及成员目标条件。测试夹具已清理。

Apifox 中成员列表、成员状态和主部门分配三个接口的说明已同步，并核对了既有请求体、响应状态和错误结构。
