# Whim 下一阶段任务计划

> 制定日期：2026-09-28。以当前 `main` 分支为基线。本文的“模块完成”指满足当前系统账号、多租户系统管理场景的验收条件；将来增加新的账号体系或业务域时，再按新需求扩展。

## 一、当前判断

Whim 已经具备多模块基础设施、Flyway 基线、登录与 ALTCHA 验证码、租户选择、角色和权限码加载、Sa-Token 会话适配。`whim-mybatisplus` 已配置分页、乐观锁、防全表操作和审计字段填充。

当前最需要的是**做出一条真正受权限控制的系统管理业务链路**。只有角色、权限数据能被安全地维护，并且接口实际执行授权判断，后续的数据权限才能有可靠的身份、角色和租户上下文。

数据权限是一项横跨功能授权、组织模型、业务数据归属、查询语义和写入校验的业务能力。MyBatis-Plus 只能承担其中的 SQL 执行接入；是否使用其现成插件、哪些 SQL 适合拦截，必须在确定 Whim 的规则和真实查询后决定。`RuoYi-Vue-Plus` 是问题清单与场景参考，不能直接成为 Whim 的架构或代码模板。

现状中需要特别记住的事实：

- 阶段 1 前，除认证接口外，系统管理 Controller 基本只有类级路由；目前成员、角色、权限、套餐等最小管理入口已按业务对象接入。
- Sa-Token 的角色、权限注解及适配器已接入阶段 1 的业务入口；当前统一登录拦截匹配 `/system/**`。
- 阶段 1 已将租户有效权限查询调整为“角色权限与当前租户套餐权限的交集”；动态结果仍需运行验收。
- `data_scope` 已进入角色信息，用户在租户中的明确部门归属、数据范围计算和 SQL 隔离尚未完成。
- `sys_user` 是全局身份表，`sys_role.tenant_id` 允许为空；不能将所有系统表简单套用同一条租户过滤规则。
- 根 POM 原为 Spring Boot `4.0.5`，阶段 0 已调整为 `4.1.1`；JDK 配置为 25，运行兼容尚未验证。
- 阶段 1 已新增 `V3`、`V4`、`V5`，分别处理 RBAC 作用域与成员状态、功能权限目录、初始平台管理员。后续数据库变更继续使用更高版本的 Flyway 迁移，不修改已存在的版本。

## 二、执行顺序与里程碑

| 顺序 | 阶段 | 交付结果 | 完成判定 |
| --- | --- | --- | --- |
| 0 | 固定基线与边界 | 版本、路由、权限和数据归属规则明确 | 后续开发不再靠临时假设确定租户或权限 |
| 1 | 功能权限 RBAC 闭环 | 可维护角色授权，接口实际校验权限 | 普通用户不能仅凭登录访问未授权的系统管理接口 |
| 2 | 组织归属与数据范围模型 | 用户部门、角色自定义部门、操作对应的数据范围语义落地 | 能从当前租户、本次操作及其授权角色确定可访问范围 |
| 3 | 认证会话收口 | 状态变化与授权变化能正确影响会话 | **`whim-satoken` 达到当前项目的完成标准** |
| 4 | 租户隔离和数据权限落地 | 业务策略与 SQL 执行衔接，真实查询和写入受到约束 | **`whim-mybatisplus` 达到当前项目的完成标准** |
| 5 | 扩展系统管理功能 | 邀请、个人资料等剩余业务功能 | 在已稳定的认证与持久化边界上继续扩展 |

按阶段完成，每一阶段通过下面的验收后再进入下一阶段。阶段 1 和阶段 2 只做支撑框架验收所需的最小业务链路，不要求一次做完所有后台页面。

- [x] 列出系统表的归属清单：全局表、租户表、平台与租户混合表。至少明确 `sys_user`、`sys_permission`、`sys_tenant`、`sys_role`、`sys_user_role`、`sys_dept`、`sys_post` 的处理方式。

阶段 0 的规则、表分类、管理员初始化方式和验收数据规格记录在 [技术基线与访问边界](阶段0-技术基线与访问边界.md)。运行兼容检查仍待完成，实际管理接口的功能授权属于阶段 1。

## 四、阶段 1：完成最小 RBAC 功能权限闭环

### 任务

- [ ] 先通过新的 Flyway 迁移落实平台角色绑定：`sys_role.tenant_id IS NULL` 与 `sys_user_role.tenant_id IS NULL` 同时表示平台作用域；租户角色及绑定都使用同一个实际租户 ID。处理历史重复绑定、唯一性约束和 Mapper 查询，再由 V5 初始化缺失的 `admin`、平台角色与绑定。迁移文件已写好，实际迁移和首位管理员写入尚未执行。
- [x] 实现必要的系统管理 API：已有租户成员查询与状态管理、角色查询与维护、用户角色分配、权限查询、角色权限分配。使用 DTO/VO，不直接把实体当作对外协议。新成员邀请仍在阶段 5。
- [x] 为这些 API 建立清晰的权限码，并在业务入口使用现有 Sa-Token 权限校验能力；平台接口和租户接口分别校验操作范围。
- [x] 处理角色、成员、权限的跨租户引用：操作目标的 `tenant_id` 必须与当前租户匹配；平台角色与租户角色不能混用。
- [x] 实现有效权限查询：有效角色授予的权限与当前租户套餐可用权限取交集；平台角色的规则单独明确。失效的用户、租户、套餐、角色、权限不产生有效授权。运行结果待验收。
- [x] 对用户角色、角色权限、租户套餐、成员状态、角色或权限状态变化实现会话失效策略。数据库事务提交成功后再使旧授权失效；失败回滚时不提前踢下线。运行结果待验收。
- [x] 明确超级管理员的功能权限边界，不让功能权限通配符自动变成跨租户数据读取权限。

### 验收

- 同一用户切换租户后只得到目标租户的有效角色与权限；租户 A 的授权不能用于租户 B。
- 套餐未包含的权限，即使角色已授予也不能通过功能权限校验。
- 没有相应权限码的用户访问受保护管理接口得到 403；没有登录得到 401。
- 角色或权限变更后的旧会话不会继续使用旧授权。

**阶段 1 完成时，功能权限 RBAC 才算闭环。** 这仍不代表数据权限已经完成。

阶段 1 的迁移、初始化步骤、API 与两租户验收清单见 [RBAC 初始化与验收](阶段1-RBAC初始化与验收.md)。当前代码实现已推进，数据库迁移、管理员写入及 401/403、跨租户、会话失效等动态场景尚未执行，因此本阶段尚未通过验收。

## 五、阶段 2：补齐组织归属与数据范围模型

### 任务

- [ ] 将“一个用户在一个租户内有一个主部门”作为当前版本的规则，明确部门归属放在租户成员关系中，而不是全局用户表中。使用新的 Flyway 迁移添加字段、索引，并处理已有成员数据。
- [ ] 校正岗位与部门的关系：当前架构文档描述岗位关联部门，但 `sys_post` 实体尚无部门字段。若岗位用于组织权限，就补齐这个关系；保持同租户约束。
- [ ] 完成租户部门树的必要维护，以及角色自定义部门范围 `sys_role_dept` 的维护入口；拒绝跨租户部门关联。
- [ ] 固定六种 `data_scope` 的业务语义：全部、自定义部门、本部门、本部门及以下、仅本人、部门及以下或本人。“全部”也只表示本次操作获授权范围内的当前租户数据。
- [ ] 建立“本次功能权限码或业务动作 → 实际授予该权限的有效角色”关系。数据范围只由这些角色参与计算；一个拥有全量数据范围但未授权本次操作的角色，不能扩大本次操作可见数据。
- [ ] 明确同一操作有多个授权角色时的合并规则。列表和详情的可读范围可以按授权角色取并集；修改、删除、分配等操作必须分别定义可操作目标规则，不直接套用读范围或照搬其他项目的拼接方式。
- [ ] 定义缺少部门、无可用角色、无当前租户、无功能权限、平台任务没有请求上下文时的拒绝规则；“仅本人”明确以业务数据的创建人或专门的负责人字段为准，不混用。
- [ ] 为首个受保护业务资源写数据权限决策表：资源、动作、当前租户、参与角色、部门/本人字段、允许范围、拒绝结果、受控例外。先审定这张表，再写 SQL 拦截逻辑。
- [ ] 使当前登录上下文中的 `deptId` 来自当前租户的有效成员归属；切换租户时重新计算。

### 验收

- 同一用户在租户 A 和 B 可以具有不同部门，切换租户后 `deptId` 正确变化。
- 角色的自定义部门范围只包含当前租户部门；部门停用、删除或转移后不会留下越权范围。
- 六种数据范围和每种操作的多角色合并规则均有明确的输入、输出示例，供阶段 4 实现 SQL 约束。
- 同一用户拥有两种角色时，一个角色有本次操作权限但范围较小，另一个角色范围为“全部”却无本次操作权限；最终只能使用前一个角色的数据范围。

## 六、阶段 3：收口 `whim-satoken`

### 任务

- [ ] 统一登录、退出、`userInfo` 租户选择、当前用户上下文、角色和权限读取的行为；同一用户的不同令牌保有各自当前租户上下文。
- [ ] 核对账号停用、租户停用或到期、成员移除、角色或权限变化、套餐变化时的会话处理；不能只在下一次登录时才失效。
- [ ] 统一 401、403、令牌过期、被踢下线及上下文缺失时的响应和中文日志；不把内部异常或敏感令牌写进日志。
- [ ] 统一 `/system/**` 的登录保护和业务接口的权限校验；审查所有放行路径。新增账号体系时只需扩展账号体系注册与对应业务实现，不让业务模块直接依赖 Sa-Token。
- [ ] 核对记住我、并发登录、令牌替换、退出、切换租户与重新获取用户信息的实际行为；保持 `whim-satoken` 与 `whim-mybatisplus` 之间无依赖。

### `whim-satoken` 完成判定

以下条件全部满足，即可把该模块视为**当前系统账号场景已完成**：

- [ ] 身份读取和会话操作只经 `whim-core` 抽象供业务使用。
- [ ] 未登录、无功能权限、令牌过期、账号或租户失效均得到稳定且正确的结果。
- [ ] 不同令牌和不同租户上下文互不串用；授权变更后旧令牌不能保留旧权限。
- [ ] 所有实际开放的系统接口都有明确的登录与功能权限边界。
- [ ] 超级管理员规则和平台、租户边界有文档与实际场景核对。

## 七、阶段 4：落地数据权限策略与 `whim-mybatisplus` 执行层

### 任务

- [ ] 先选一个真实的租户业务资源作为落地样本，确保其数据具备 `tenant_id`，且部门范围、本人范围各有明确字段。不要用全局身份表 `sys_user` 冒充租户业务数据。
- [ ] 按阶段 2 的决策表实现业务策略：`whim-system` 负责判断本次动作可使用哪些授权角色、部门和本人范围；`whim-core` 只承载必要的中立契约；`whim-mybatisplus` 负责把已确定的范围施加到持久化操作，不在拦截器里重新查询角色业务。
- [ ] 对租户业务表建立默认租户隔离；当前租户缺失时拒绝租户业务查询和写入。全局表、平台操作、`sys_role` 等混合表分别制定显式规则，不采用无审查的全局忽略。
- [ ] 先审查实际 Mapper SQL、表别名、联表、子查询、分页总数和批量操作，再决定使用 MyBatis-Plus 的租户/数据权限插件、显式 Mapper 条件，或两者组合。插件是执行工具，不能代替业务范围判定。
- [ ] 按阶段 2 的语义，把本次操作的有效数据范围转换为可检查的 SQL 条件；核对单表、联表、分页列表、分页总数、详情、导出等读操作是否得到同一范围。
- [ ] 对修改、删除、状态变更和关系分配分别校验目标记录、目标租户及操作权限。按 ID 操作和批量操作都要有明确的目标范围规则；不能只凭列表查询过滤来推断写操作安全。
- [ ] 定义数据范围计算所需的部门树、自定义部门查询与缓存更新方式，避免拦截器中的递归查询、缓存陈旧或从其他租户取到部门 ID。
- [ ] 对嵌套 Mapper 调用、事务、虚拟线程和后台任务明确上下文的建立、传递与清理；没有上下文时默认拒绝受保护操作。确需绕过时限定入口、原因和调用方权限，并保证结束后恢复原状态。
- [ ] 核对拦截器顺序与现有分页、乐观锁、防全表操作的组合；核对审计字段、逻辑删除及软删除时的删除人和删除时间。
- [ ] 对高频权限查询检查索引和执行计划，重点关注 `tenant_id`、`dept_id`、`create_by` 和关联表的查询路径；只按实际 SQL 增补索引。
- [ ] 保持 `whim-satoken` 与 `whim-mybatisplus` 独立；MyBatis 模块不直接读取 Sa-Token、HTTP 请求或系统领域实体。

### `whim-mybatisplus` 完成判定

以下条件全部满足，即可把该模块视为**当前多租户数据访问场景已完成**：

- [ ] 租户 A 无法通过列表、详情、分页、联表、按 ID 更新或删除访问租户 B 的业务数据。
- [ ] 六种数据范围按“当前动作的授权角色”计算；无本次操作权限的全量角色不会放大可见范围，缺少上下文时默认拒绝。
- [ ] 分页总数与列表使用同一权限条件；详情、导出、越权写入与关联修改分别通过目标场景核对。
- [ ] 全局表和平台接口仍按其专属规则工作，例外路径有明确权限检查。
- [ ] 嵌套调用、后台任务及受控绕过后不会泄漏或遗留数据权限上下文。
- [ ] 审计字段、逻辑删除、乐观锁、防全表操作与租户和数据权限组合后仍符合预期。
- [ ] SQL 可读、可解释，必要索引已与实际查询对应；模块边界仍保持独立。

## 九、每阶段的工作方式

1. 先读取相关 Controller、Service、Mapper、XML、Entity 与表定义，再改动对应的最小范围。
2. 数据库变更只新增 Flyway 版本，准备回填与兼容策略，不改 `V1`、`V2`。
3. 每个阶段记录改动文件、关键 SQL 和验收结果。至少用平台管理员、两租户、两角色、不同套餐、无权限用户核对边界。
4. 遵守项目约束：不执行 Java 或 Maven 命令；除非另有明确要求，不编写测试代码。未执行的构建或运行验证要如实记录，不能视为已通过。
