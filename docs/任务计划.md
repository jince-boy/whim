# Whim 下一阶段任务计划

> 制定日期：2026-09-28。以当前 `main` 分支为基线。本文的“模块完成”指满足当前系统账号、多租户系统管理场景的验收条件；将来增加新的账号体系或业务域时，再按新需求扩展。

## 一、当前判断

Whim 已经具备多模块基础设施、Flyway 基线、账号密码登录、租户选择、角色和权限码加载、Sa-Token 会话适配。`whim-mybatisplus` 已配置分页、乐观锁、防全表操作和审计字段填充。

当前最需要的是**做出一条真正受权限控制的系统管理业务链路**。只有角色、权限数据能被安全地维护，并且接口实际执行授权判断，后续的数据权限才能有可靠的身份、角色和租户上下文。

数据权限是一项横跨功能授权、组织模型、业务数据归属、查询语义和写入校验的业务能力。MyBatis-Plus 只能承担其中的 SQL 执行接入；是否使用其现成插件、哪些 SQL 适合拦截，必须在确定 Whim 的规则和真实查询后决定。`RuoYi-Vue-Plus` 是问题清单与场景参考，不能直接成为 Whim 的架构或代码模板。

现状中需要特别记住的事实：

- 阶段 1 前，除认证接口外，系统管理 Controller 基本只有类级路由；目前成员、角色、权限、套餐等最小管理入口已按业务对象接入。
- Sa-Token 的角色、权限注解及适配器已接入阶段 1 的业务入口；当前统一登录拦截匹配 `/system/**`。
- 阶段 1 已将租户有效权限查询调整为“角色权限与当前租户套餐权限的交集”；两租户动态验收已验证该规则与 HTTP 错误状态。
- `data_scope`、用户在租户中的主部门归属和按本次权限计算范围已落地；当前已开放的岗位、部门、成员资源均通过动作数据范围验收。将来新增业务资源时仍需逐项接入。
- `sys_user` 是全局身份表，`sys_role.tenant_id` 允许为空；不能将所有系统表简单套用同一条租户过滤规则。
- 根 POM 原为 Spring Boot `4.0.5`，阶段 0 已调整为 `4.1.1`；使用 JDK 25 构建与启动后，Web、Flyway、Sa-Token、MyBatis-Plus、Redisson 的运行链路已经过动态验收。
- 阶段 1 已新增 `V3`、`V4`、`V5`，分别处理 RBAC 作用域与成员状态、功能权限目录、初始平台管理员。后续数据库变更继续使用更高版本的 Flyway 迁移，不修改已存在的版本。
- `V7` 为尚无租户的安装预置默认租户、套餐与初始租户管理员授权。只使用 RBAC 的项目仍以这个租户作为内部作用域；增加租户后沿用相同的账号、成员和角色模型。已有租户的部署不会被迁移接管。V8 接入岗位资源，V9 补齐岗位成员权限；部门和租户成员使用显式数据范围规则。

## 二、执行顺序与里程碑

| 顺序 | 阶段 | 交付结果 | 完成判定 |
| --- | --- | --- | --- |
| 0 | 固定基线与边界 | 版本、路由、权限和数据归属规则明确 | 后续开发不再靠临时假设确定租户或权限 |
| 1 | 功能权限 RBAC 闭环 | 可维护角色授权，接口实际校验权限 | 普通用户不能仅凭登录访问未授权的系统管理接口 |
| 2 | 组织归属与数据范围模型 | 用户部门、角色自定义部门、操作对应的数据范围语义落地 | 能从当前租户、本次操作及其授权角色确定可访问范围 |
| 3 | 认证会话收口 | 状态变化与授权变化能正确影响会话 | **`whim-satoken` 达到当前项目的完成标准** |
| 4 | 租户隔离和数据权限落地 | 业务策略与 SQL 执行衔接，真实查询和写入受到约束 | **`whim-mybatisplus` 达到当前项目的完成标准** |
| 5 | 扩展系统管理功能 | 邀请、个人资料等剩余业务功能 | 在已稳定的认证与持久化边界上继续扩展 |

按阶段完成，每一阶段通过下面的验收后再进入下一阶段。阶段 1 和阶段 2 只做支撑框架验收所需的最小业务链路，不要求一次做完所有后台页面。

## 四、阶段 1：完成最小 RBAC 功能权限闭环

### 任务

- [x] 通过 Flyway 迁移落实平台角色绑定：`sys_role.tenant_id IS NULL` 与 `sys_user_role.tenant_id IS NULL` 同时表示平台作用域；租户角色及绑定都使用同一个实际租户 ID。历史绑定清理和唯一性约束由迁移处理；本地测试库已执行到 V5，初始 `admin` 与平台角色绑定已核对。
- [x] 实现必要的系统管理 API：已有租户成员查询与状态管理、角色查询与维护、用户角色分配、权限查询、角色权限分配。使用 DTO/VO，不直接把实体当作对外协议。新成员邀请仍在阶段 5。
- [x] 为这些 API 建立清晰的权限码，并在业务入口使用现有 Sa-Token 权限校验能力；平台接口和租户接口分别校验操作范围。
- [x] 处理角色、成员、权限的跨租户引用：操作目标的 `tenant_id` 必须与当前租户匹配；平台角色与租户角色不能混用。
- [x] 实现有效权限查询：有效角色授予的权限与当前租户套餐可用权限取交集；平台角色的规则单独明确。失效的用户、租户、套餐、角色、权限不产生有效授权。两租户动态结果已核对。
- [x] 对用户角色、角色权限、租户套餐、成员状态、角色或权限状态变化实现会话失效策略。数据库事务提交成功后再使旧授权失效；失败回滚时不提前踢下线。动态测试已核对变更与强制回滚场景。
- [x] 明确超级管理员的功能权限边界，不让功能权限通配符自动变成跨租户数据读取权限。

### 验收

- 同一用户切换租户后只得到目标租户的有效角色与权限；租户 A 的授权不能用于租户 B。
- 套餐未包含的权限，即使角色已授予也不能通过功能权限校验。
- 没有相应权限码的用户访问受保护管理接口得到 403；没有登录得到 401。
- 角色或权限变更后的旧会话不会继续使用旧授权。

**阶段 1 完成时，功能权限 RBAC 才算闭环。** 这仍不代表数据权限已经完成。

阶段 1 的迁移、初始化步骤、API 与两租户验收清单见 [RBAC 初始化与验收](阶段1-RBAC初始化与验收.md)，实际运行结果见[动态验收报告](阶段1-RBAC动态验收报告.md)。83 项动态检查全部通过，阶段 1 已完成验收；下一步按阶段 2 建立组织归属与数据范围模型。

## 五、阶段 2：补齐组织归属与数据范围模型

### 任务

- [x] 将“一个用户在一个租户内有一个主部门”作为当前版本的规则，明确部门归属放在租户成员关系中，而不是全局用户表中。V6 迁移添加字段与索引；历史成员保持空归属，不推断错误部门。
- [x] 校正岗位与部门的关系：V6 和实体已加入 `sys_post.dept_id`；岗位写入入口已校验部门属于当前租户且处于本次操作范围内。
- [x] 完成租户部门树的必要维护，以及角色自定义部门范围 `sys_role_dept` 的维护入口；拒绝跨租户部门关联。
- [x] 固定六种 `data_scope` 的业务语义：全部、自定义部门、本部门、本部门及以下、仅本人、部门及以下或本人。“全部”也只表示本次操作获授权范围内的当前租户数据。
- [x] 建立“本次功能权限码或业务动作 → 实际授予该权限的有效角色”关系。数据范围只由这些角色参与计算；一个拥有全量数据范围但未授权本次操作的角色，不能扩大本次操作可见数据。
- [x] 明确同一操作有多个授权角色时的合并规则。列表和详情的可读范围按授权角色取并集；修改、删除、分配等操作分别定义可操作目标规则。
- [x] 定义缺少部门、无可用角色、无当前租户、无功能权限、平台任务没有请求上下文时的拒绝规则；“仅本人”以明确的业务数据字段为准。
- [x] 为首个受保护业务资源 `sys_post` 写数据权限决策表；阶段 4 按此表实现 SQL 与写目标校验。
- [x] 使当前登录上下文中的 `deptId` 来自当前租户的有效成员归属；切换租户时重新计算。

### 验收

- 同一用户在租户 A 和 B 可以具有不同部门，切换租户后 `deptId` 正确变化。
- 角色的自定义部门范围只包含当前租户部门；部门停用、删除或转移后不会留下越权范围。
- 六种数据范围和每种操作的多角色合并规则均有明确的输入、输出示例，供阶段 4 实现 SQL 约束。
- 同一用户拥有两种角色时，一个角色有本次操作权限但范围较小，另一个角色范围为“全部”却无本次操作权限；最终只能使用前一个角色的数据范围。

阶段 2 在当前组织模型与岗位样本范围内已完成：六种数据范围的真实接口矩阵 168/168 通过，组织管理接口 38/38 通过。清除成员主部门时 `NULL` 未落库的问题已经修复并复测；后续阶段 4 的数据库已执行到 V9。验收明细见[组织归属与数据范围规则](阶段2-组织归属与数据范围规则.md)。
