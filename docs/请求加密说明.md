# 请求加密说明

后端统一管理 RSA 密钥，前端运行时自动获取公钥。日常开发、前端打包和后端打包均无需生成、复制或配对密钥。公共请求层自动加密 JSON 请求，后端识别并解密；业务调用保持原样，响应不加密。

## 密钥管理

后端首次启动自动生成 3072 位 RSA 私钥，保存到 `whim.request-encryption.private-key-file` 指定的文件；后续启动直接复用，不随重新打包或重启变化。默认配置：

```yaml
whim:
  request-encryption:
    private-key-file: ./data/keys/request-encryption-private.key
    max-body-bytes: 65536
    requests-per-minute: 120
```

本地路径相对于后端进程的工作目录，开发工具中应保持工作目录一致。私钥文件为 PKCS#8 DER 的单行 Base64，不能放在可通过 HTTP 下载的上传目录。`data/keys` 已加入 Git 忽略规则，不进入后端镜像。Linux 自动创建的密钥目录权限为 `0700`、文件权限为 `0600`；Windows 使用目录的访问控制权限。

Docker Compose 已把容器 `/app/data/keys` 挂载到宿主机 `/opt/whim/backend/keys`，首次启动会自动准备目录和写权限。升级镜像、重新创建容器时保留并备份该目录即可，不需要填写私钥。目录不可写、已有密钥无效或读取失败时终止启动，不覆盖已有文件。初始化使用文件锁和原子写入，避免共用目录的进程同时生成不同密钥。文件锁需要文件系统支持，锁文件保留在密钥目录中，不要手动删除。

已有密钥也可以通过 `whim.request-encryption.private-key` 或环境变量 `WHIM_REQUESTENCRYPTION_PRIVATEKEY` 注入；填写时优先使用该密钥，不读写自动管理的文件。私钥必须是至少 3072 位 RSA 的 PKCS#8 DER 单行 Base64，不带 PEM 头尾或换行。无需在 YAML 中保存私钥，前端也没有任何密钥配置项。

多实例必须使用相同私钥：共享支持文件锁的持久化目录，或将同一份私钥文件预先分发到所有实例；不能让不同服务器各自生成独立密钥后接入同一负载均衡器。需要预生成文件时，可以在项目根目录执行可选工具：

```shell
node scripts/generateRequestKey.mjs
```

也可以用第一个参数指定目标文件路径。脚本仅将新私钥写入文件，不输出私钥内容，不覆盖已有文件；单实例开发和部署无需执行。

需要主动轮换时，停止使用该密钥的全部后端实例，备份并替换私钥文件，再启动实例；若使用外部注入，则同步更新各实例的注入值。浏览器刷新页面后自动获取新公钥，无需重新构建前端。旧页面持有旧公钥，轮换后需要刷新；不要在滚动发布时混用不同密钥。

## 公钥接口

`GET /system/auth/requestEncryptionKey` 无需登录、无需参数或请求体，响应使用统一 `Result<String>`。`data` 是与当前私钥对应的 SPKI DER 单行 Base64 公钥，响应头为 `Cache-Control: no-store`。接口仅返回公钥，不暴露私钥。

前端首次发送 JSON 加密请求前通过公共 HTTP 客户端调用该接口，并发请求共用一次初始化；成功后在当前页面内存中复用，刷新页面后重新获取。获取失败时停止当前业务请求，不回退明文；后续操作可重新获取。GET、文件和表单请求无需等待公钥。前端 Dockerfile、Compose 和 `.env` 均不再接收 `VITE_REQUEST_ENCRYPTION_PUBLIC_KEY`。

从旧版固定公钥方案升级时，需一次性发布这次修改的前后端以及后端 Compose，并刷新浏览器，保证新前端能够访问公钥接口；之后常规构建不再需要配对密钥。部署步骤见[部署指南](部署指南.md)。

## 业务使用

前端继续调用统一的 `request()`，例如登录仍使用：

```typescript
login({ username, password, uuid, captchaCode })
```

公共层自动处理 POST、PUT、PATCH、DELETE 中的 JSON 对象或数组。GET、无请求体请求、文件及表单上传保持原有方式。当前登录、菜单新增/修改、字典新增/修改/导出的 JSON 请求均自动加密。加密失败时终止发送，不回退明文。

后端在需要强制拒绝明文的接口上添加 `com.whim.core.annotation.RequestDecrypt`。登录已有该注解：

```java
/**
 * 解密并校验登录参数后返回认证信息，密码保持原始字符。
 *
 * @param loginDTO 登录参数
 * @return 登录结果
 */
@PostMapping("/login")
@RequestDecrypt
@XssIgnore
public Result<AuthenticationToken> login(@RequestBody @Valid AuthLoginDTO loginDTO) {
    return Result.success("登录成功", authService.login(loginDTO));
}
```

- 有注解：必须提交密文，明文或错误格式返回 HTTP 400。
- 无注解：自动解密密文，也兼容原来的业务 JSON。
- 解密发生在 XSS 清洗和 DTO 校验之前。登录使用 `@XssIgnore` 保留密码特殊字符，其他接口沿用已有清洗规则。
- `encryptedData` 为框架保留的顶层字段。JSON 请求体默认最多 65536 字节，密文按完整包装体计算。所有密文解密按客户端 IP 合计限流，默认 120 次/分钟；登录原有业务限流继续生效。

## 模块职责

- `whim-core`：注解、密钥生成和持久化、公钥导出、JWE 密码学校验与解密。
- `whim-web`：HTTP 请求解析、注解检查、过滤器、长度限制和分布式解密限流。
- 应用认证控制器：提供无需登录的公钥接口，放行路径在 `application.yml` 中配置。
- 前端公共请求层：运行时获取公钥并自动加密 JSON。

## HTTP 格式

使用后端当前公钥加密下列 UTF-8 JSON：

```json
{
  "method": "POST",
  "path": "/system/auth/login",
  "body": {
    "username": "",
    "password": "",
    "uuid": "",
    "captchaCode": ""
  }
}
```

`method` 为实际 HTTP 方法的大写形式。`path` 使用实际路径变量值，不含反向代理前缀或 Servlet context path。加密请求的业务参数全部放在 Body 中，不附带查询参数或 Content-Encoding。

标准 JWE Compact 算法固定为 `RSA-OAEP-256` + `A256GCM`。浏览器提供 SubtleCrypto 时使用 `jose`；HTTP 页面缺少该能力时按需加载 `node-forge` 兼容实现。每次加密使用新的 256 位 AES 密钥、96 位 IV 和 RSA-OAEP 随机种子，随机数来自浏览器密码学随机源 `crypto.getRandomValues`，不回退到 `Math.random`。受保护头包含 `alg`、`enc`、`kid`（公钥 RFC 7638 SHA-256 指纹）、`typ: whim-request+jwe` 和 `cty: application/json`。两种前端实现保持相同协议，后端拒绝其他算法、错误指纹、压缩和未知关键头。

向原业务接口直接发送 `Content-Type: application/json`：

```json
{
  "encryptedData": "五段以点分隔的 JWE 密文"
}
```

登录在获取验证码后提交；当前页面第一次发送加密 JSON 时会先自动获取公钥。其业务字段定义、校验规则及真实线上的密文包装格式均维护在 Apifox Body 中；不创建调试用例。文档示例不代表运行页已填入可用密文。

HTTP 400 表示明文被拒绝、JSON 或密文无效、请求体过大、密钥或目标不匹配，以及原有参数校验失败；HTTP 429 表示限流。身份、权限和其他业务错误沿用现有规则。响应保持原有 JSON 或文件下载格式。

HTTP 与 HTTPS 均可使用当前请求加密。公钥获取和应用层加密不能提供 TLS 的服务器身份校验，也不保护响应或令牌传输，生产部署应使用 HTTPS。此简化方案不提供一次性凭证或通用防重放能力，登录验证码仍按原业务流程校验和消费。业务代码不记录密码、解密请求体或密钥。

协议参考：[RFC 7516](https://www.rfc-editor.org/rfc/rfc7516)、[RFC 7638](https://www.rfc-editor.org/rfc/rfc7638)、[jose](https://github.com/panva/jose)。
