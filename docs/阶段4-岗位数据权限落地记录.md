# 阶段 4：岗位数据权限落地记录

## 已接入的边界

`sys_post` 是首个具有 `tenant_id`、`dept_id` 和明确本人字段 `create_by` 的租户业务资源。六个业务动作分别使用 `system:post:list/detail/create/update/status/delete`，先从实际授予本次权限的有效租户角色计算范围，再执行对应数据操作。平台超级管理员的功能权限通配符不能代替岗位数据范围；缺少本次动作授权角色时直接拒绝。

- 分页列表与分页总数由同一个带当前租户和数据范围的查询条件产生；详情按对应详情权限单独计算范围。
- 创建由服务端设置租户与创建人；指定的部门必须是当前租户有效部门，并落在本次创建权限范围内。仅本人分支允许不归属部门或归入本人有效主部门。
- 修改、启停先查本次动作可见的原目标，写入语句再次限制租户和数据范围。修改部门时同时校验新部门的范围。
- 删除使用显式 SQL，在同一语句里检查目标租户、范围、逻辑删除状态和有效岗位成员关联，写入删除人及删除时间。

数据范围 1 到 6 的业务含义和多角色并集仍以[阶段 2 规则](阶段2-组织归属与数据范围规则.md)为准。岗位业务采用显式服务条件和一条明确的删除 SQL，以便逐条审查分页、详情与写目标；没有把 MyBatis-Plus 数据权限插件当成权限决策器。V8 添加 `tenant_id + create_by` 与 `tenant_id + sort + id` 索引，并为 V7 初始化的默认租户配置岗位权限。其他租户仍需在套餐与角色中显式授权。

对同一个写动作，Whim 将实际授予该动作的有效角色范围取并集，再与当前租户条件相交；更新原目标和新部门都须通过本次动作的范围。对照 RuoYi-Vue-Plus 的 SQL 拦截、空范围和临时忽略处理后，本样本选择直接传递已算好的范围，不使用线程局部权限状态，因此嵌套查询不会继承一次临时忽略标记。通用 Mapper 的默认隔离仍属后续工作。

## 本地部署与动态验收

在独立临时 MySQL 库顺序执行 V6、V7、V8，验证了默认租户权限、新索引和基本 SQL 边界。随后以 JDK 25 和 Spring Boot 4.1.1 打包当前代码并重启本地 `8089` 服务；本地 `whim` 库的 Flyway 历史已包含成功的 V6、V7、V8，启动时 Flyway 对全部 8 个版本校验成功。健康检查返回 HTTP 200，MySQL 与 Redis 均为 `UP`。正式动态验收前保存了完整数据库快照 `whim_backup_v8_20260929_165703`，含 17 张表、93 行；快照反映的是 V8 状态。

使用默认租户管理员和临时普通成员，通过真实验证码、登录、令牌和岗位接口执行了 **42 项检查，42 项通过**。检查覆盖分页总数与记录一致、部门子树和本人范围并集、不同操作使用各自授权角色、平台管理员通配符不产生跨租户岗位数据范围、跨租户读写拒绝、创建与修改、岗位状态、关联成员阻止删除、软删除审计、已撤销角色或套餐授权不能被旧令牌绕过，以及 HTTP 错误状态与响应体 `code` 一致。完整结果见[动态验收明细](阶段4-岗位数据权限动态验收明细.json)。临时租户、用户、角色、部门、岗位和绑定均已清理，业务表无临时数据残留。

验收发现已软删除岗位的编码仍受数据库唯一索引约束，而原服务只检查未删除记录，会返回 HTTP 500。现改为检查包含软删记录的编码占用，并把并发唯一键冲突转换为 HTTP 400；重打包、重启后已复测通过。Apifox `whim` 项目的岗位创建、修改接口说明已同步，并回读确认。

岗位样本已经通过应用级验收；其他租户业务表、通用持久化执行边界、后台任务上下文、联表及批量操作规则仍在任务计划阶段 4 中，整个数据权限与 `whim-mybatisplus` 模块尚未达到完成判定。

## 随后的执行层与岗位成员工作

已在 `whim-mybatisplus` 为经过 SQL 审核的 `sys_post` 配置默认租户拦截，租户 ID 只从 `whim-core` 认证上下文取得；未登录或未选择租户时拒绝访问。`sys_user` 为全局账号表，`sys_role` 混合平台和租户角色，`sys_dept` 被登录期查询使用，不能直接套用同一拦截规则。实际 SQL 日志确认，分页总数、列表、详情、更新和软删均附加当前租户条件。接入拦截器后重跑岗位、六范围、组织和会话矩阵，共 302/302 通过。这是 `sys_post` 的实证，不代表所有业务表已受默认隔离。

岗位成员查询和覆盖式分配已经放在岗位控制器和岗位服务中，分别使用 `system:post:member:list` 与 `system:post:member:assign`。分配前按该动作的数据范围验证岗位，并验证全部目标用户为当前租户的有效成员且全局账号已启用；空集合清空关联，恢复软删绑定时填写审计字段。V9 仅增加这两个权限码并延续初始化默认租户的授权，其他租户仍须自行配置套餐与角色。源码已通过 JDK 25 编译和打包，Apifox 两个接口的路径、参数、响应与权限说明已写入并回读。

本次后台启动命令曾被自动执行策略拒绝；改用可监控的前台会话后，应用成功启动，Flyway 已应用 V9。岗位成员接口经过 **45/45** 项真实 HTTP 与数据库核对：两租户岗位和成员边界、按成员查看与分配动作分别计算数据范围、停用成员与账号拒绝、批量失败不改原绑定、软删和恢复审计、清空后删除岗位均通过，见[岗位成员验收明细](阶段4-岗位成员动态验收明细.json)。在 V9 服务上重跑原岗位 42/42、六范围 168/168、组织 38/38、会话 54/54，合计 **347/347**。最初原岗位脚本有两项把岗位权限码数量固定为 6 的旧断言，V9 新增两码后脚本误报；按原六码修正断言并复跑通过。当前 Flyway 版本为 V9，临时业务数据已经清理。
