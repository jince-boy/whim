# 用户管理说明

用户管理采用左侧部门树、右侧分页列表。点击部门查询该部门及全部下级部门的可见用户；“全部用户”不限制部门，“未分配部门”仅查询主部门为空的用户。搜索支持用户名、姓名、联系电话、状态，切换部门回到第一页，重置搜索保留部门选择。

列表仅展示状态，行内按顺序直接显示编辑、删除、修改密码、分配角色四个操作，删除使用红色文字并保留确认弹窗。超级管理员默认拥有全部操作权限，普通账号按精确权限码显示操作。超级管理员不需要分配角色，对应按钮禁用；普通管理员不能维护超级管理员账号。遵循前端操作列规范：不超过4项时全部直接显示，超过4项时显示前三项及第四个“更多”按钮，编辑和删除优先保留在外部。新增与编辑使用公共表单弹窗，维护姓名、主部门、多个岗位、联系方式、性别、状态和备注；岗位不隐式授予角色。用户名仅在新增时填写，统一存储为小写，删除后不可复用。创建时间复用公共审计字段与自动填充处理器。

## 接口

所有接口要求系统登录，使用 `Authorization: Bearer <accessToken>`，返回项目统一 `Result<T>`。GET 筛选通过查询参数提交，JSON 请求中 ID 和操作参数统一放在 Body。

| 方法 | 路径 | 功能权限 | 说明 |
| --- | --- | --- | --- |
| GET | /system/user/page | system:user:list | 用户分页 |
| GET | /system/user/detail | system:user:detail | 编辑回填及当前岗位 |
| POST | /system/user/add | system:user:create | 新增用户和岗位关系 |
| PUT | /system/user/update | system:user:update | 编辑资料、部门、状态与岗位 |
| PUT | /system/user/resetPassword | system:user:resetPassword | 修改密码 |
| DELETE | /system/user/delete | system:user:delete | 删除用户和关联关系 |
| GET | /system/userRole/list | system:userRole:list | 当前角色及可分配角色 |
| PUT | /system/userRole/assign | system:userRole:assign | 提交完整角色集合 |

分页使用 `pageNum/pageSize`，默认 1/10，每页最多100条。`deptId` 包含下级部门；`unassigned=true` 与 `deptId` 互斥。超级管理员使用全部数据范围，普通账号的数据权限按当前确切操作的角色取并集，用户“本人”范围使用用户 ID，部门范围使用主部门 ID。

新增必须提供 `username/name/password`，性别、状态省略时默认0，岗位省略时默认为空集合。编辑必须提供 `id/name/gender/status`。`deptId/email/phone/remark` 省略或 null 表示清空，`postIds` 省略或空数组表示清空岗位，不能为 null。角色接口只接收 `id/roleIds`，角色集合省略或空数组表示清空，不能为 null。岗位与角色集合最多100项，元素不能为 null。

请求不接收审计字段；响应不包含密码或密码哈希。密码保留原输入，长度8～72个字符，不包含空白，UTF-8编码最多72字节，使用现有 BCrypt 工具保存哈希。详情返回现有停用岗位用于回显，新增任职必须校验岗位、部门分支的有效性与本次操作的数据范围。

## 关系和授权约束

- 用户最多有一个主部门，也可以未分配部门。正常用户的主部门及全部祖先必须正常。
- 用户调部门、停用或删除前，检查是否仍担任部门负责人；存在负责人关系时拒绝操作，先在部门管理中调整负责人。
- 超级管理员是独立账号身份，保存在 `sys_user.super_administrator` 中，默认拥有全部操作、有效菜单和全部数据权限，无须配置角色。普通账号继续按角色菜单关联和当前操作的数据范围校验。运行时不根据固定用户名、用户ID或角色编码判断身份。
- `superAdministrator` 仅在用户列表、详情和本人资料响应中回显；普通新增、修改、个人资料及角色分配DTO均不接收此字段，持久化字段也禁止业务插入或更新，避免通过资料维护提升身份。普通管理员不能维护超级管理员账号。
- 角色候选包含全部正常角色和目标用户已有角色；已有停用角色可回显、保留或移除，新增分配只允许正常角色。操作者拥有角色分配权限且目标用户在对应数据范围内时即可调整，无须自身持有所选角色。
- 普通账号不能调整自身角色、部门、岗位；查询自身角色时全部选项只读。超级管理员无须分配角色，可以调整自己的部门和岗位，仍须满足部门、岗位及负责人关系等业务约束。所有账号均不能删除或停用当前登录账号。
- 用户资料修改、密码修改、角色变化与删除完成后，在事务提交后失效目标用户全部登录会话。角色无变化时不重复写入或失效会话。
- 用户写入、岗位关系和角色关系维护共用现有组织锁与服务事务；删除用户时原子移除岗位和角色关系，保留用户名全局唯一约束。
- 参数校验失败返回400，未登录401，功能权限或归属越权403，用户名冲突409，记录不可见及业务约束失败500，HTTP状态与 Result.code 一致。

部门树复用部门查询接口，岗位选项复用岗位分页接口并支持搜索与继续加载；分别需要 `system:dept:list` 和 `system:post:list`。没有候选查询权限时保留原有归属与岗位回显，不静默清空。

## 数据库迁移与验证

`V6__enable_user_management.sql` 将用户主部门改为可空，补充真实性别字典 `sys_user_gender`，清理未使用的独立用户部门、状态权限入口。部署时由 Flyway 执行新迁移，不修改已有版本脚本。

`V14__separate_super_administrator_identity.sql` 将旧版有效超级管理员角色成员转换为独立账号身份，清理旧角色的菜单、部门、用户关联并逻辑删除旧角色。角色列表和候选项通过正常逻辑删除规则自然排除该角色，不使用固定ID或编码隐藏。历史迁移保持不变，V14完成后超级管理员不再依赖V13建立的授权关系。升级后旧登录快照不再参与授权，需要重新登录；以后新增菜单和操作无需再给超级管理员授权，普通账号仍需明确分配。

前端类型检查及 ESLint 通过。浏览器已检查部门树、列表布局和新增表单；当前运行后端尚未加载新增接口，返回404，因此未完成保存及角色分配的运行联调。遵循项目规则，未执行 Java/Maven 命令，未新增测试代码。

Apifox `whim / main / 用户管理` 已维护上述8个接口，JSON Body 定义、必填项、约束及示例经过 OpenAPI 导出核对，未创建调试用例。
