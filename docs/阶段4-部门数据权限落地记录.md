# 阶段 4：部门数据权限落地记录

## 部门范围语义

部门是组织结构节点，其授权归属是本部门的 `id`。`system:dept:list/create/update/status` 各自从实际授予本次权限的有效租户角色计算数据范围；其他动作的全量角色不能扩大本动作范围。范围 1 可操作当前租户全部部门；范围 2、3、4、6 只使用算出的部门 ID，范围 6 的本人分支在部门资源上没有可比较的业务所有者。“仅本人”范围 5 也不把审计字段 `create_by` 当作部门所有权，因此单独授予它时返回 403。

列表只返回允许的节点，可能是部门树的一部分；客户端可以把未返回父节点的可见节点当作当前可见根节点。创建根部门仅允许本次创建动作的全部范围；创建子部门要求父节点属于当前租户、整条实际祖先链有效且父节点在本次范围内。修改名称、排序和状态前先检查目标范围，最终更新语句再次限制目标 ID 与租户 ID。跨租户目标和父部门均拒绝。

`sys_dept` 还服务于登录、成员主部门与角色范围计算，不能把它无条件加入通用租户 SQL 拦截器。对外管理入口显式校验租户与动作范围；内部认证查询按其自身调用约束处理。为避免角色范围服务与部门服务互相依赖，祖先链校验放入 `SysDeptPathService`，数据范围合并放入 `SysDataScopeService`；角色服务保留原有对外契约。范围查询每次读取数据库，不缓存部门树或角色决定，变更后不会命中陈旧范围。

## 动态验收

独立两租户数据覆盖六种范围的部门列表、根/子部门创建、修改、状态变更、跨租户拒绝、自定义部门祖先停用、成员主部门为空，以及不同操作使用不同授权角色；**57/57** 项通过，见[部门范围验收明细](阶段4-部门数据权限动态验收明细.json)。在这次改动的服务版本上，岗位六范围 168/168、原岗位 42/42、岗位成员 45/45、组织接口 38/38、会话 54/54、记住我 9/9、租户到期 6/6 同时回归通过，合计 **419/419**。临时租户、用户、角色、部门、岗位和绑定均已清理；Flyway 仍为 V9，MySQL 与 Redis 健康检查均为 `UP`。

Apifox 的四个部门接口说明已同步“本次动作范围”“仅本人无部门所有者”和根部门创建规则。现有业务 SQL 中，岗位由 SQL 拦截器追加默认租户条件并由服务条件施加六种范围；部门与混合授权表采用显式条件，未使用参考项目的注解、线程局部忽略标记或 SQL 模板。
