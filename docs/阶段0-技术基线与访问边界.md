# 阶段 0：技术基线与访问边界

> 2026-09-28。对应 [任务计划](任务计划.md) 的阶段 0。本文件确定接下来实现功能权限和数据权限时共同遵守的边界；具体授权接口与数据迁移在后续阶段落地。

## 技术基线

- JDK 25；根 POM 的 Spring Boot 父版本为 `4.1.1`。该版本列在 [Spring Boot 官方稳定版本文档](https://docs.spring.io/spring-boot/reference/) 中。
- Web、Sa-Token、MyBatis-Plus、Flyway、Redis 分别继续由现有模块集成。`whim-satoken` 与 `whim-mybatisplus` 都只依赖 `whim-core` 的必要抽象，不能相互依赖。
- 当前仅能完成 POM、源码、配置和自动配置注册的静态核对。项目规则禁止执行 Java/Maven 命令，因此 Spring Boot 4.1.1 下的依赖解析、启动与外部服务连接尚未验证，不能记为通过。
- 数据库变更从当前 `V2` 之后新增迁移版本；已存在的 `V1`、`V2` 不修改。

## HTTP 路由边界

系统管理接口统一放在 `/system/**`。认证接口使用 `/system/auth`；用户、角色、权限、租户、部门、岗位、配置分别使用 `/system/user`、`/system/role`、`/system/permission`、`/system/tenant`、`/system/dept`、`/system/post`、`/system/config` 等 lower camel case 路径。关联操作归入所属主体的子资源，例如角色权限使用 `/system/role/{roleId}/permissions`。阶段 0 只统一类级路由，具体管理方法在后续阶段增加。

- `/system/auth/login` 是公开认证入口；放行配置由 `application.yml` 维护。
- `/system/auth/logout`、`/system/auth/userInfo` 以及其他 `/system/**` 接口要求登录；未来新增操作还须校验功能权限和目标资源范围。
- API 路径、请求体或请求头中提供的租户 ID 不能单独作为授权依据。普通租户业务使用当前令牌的 `currentTenantId`，并校验该用户对此租户的有效访问权。
- 平台接口需要明确的平台权限；`currentTenantId == null` 可能只是用户尚未选择租户，不能据此认定其具有平台管理权限。

## 系统表归属清单

“全局”表示其主体数据不归属于某一个租户，不表示任意登录用户可以访问。带 `tenant_id` 的关联表也要按操作语义校验，不能只看字段存在与否来配置 SQL 拦截。

| 表 | 类型 | 访问规则 |
| --- | --- | --- |
| `sys_user` | 全局身份 | 登录服务按账号读取；租户管理员通过本租户成员关系管理成员，不直接获得全局用户表的任意修改权。 |
| `sys_tenant` | 平台租户目录 | 平台管理租户生命周期；租户管理接口只读取或修改已授权的本租户资料。 |
| `sys_tenant_package` | 全局套餐目录 | 平台维护；租户只读取本租户套餐及有效能力。 |
| `sys_tenant_package_permission` | 全局套餐权限关系 | 平台维护；参与有效功能权限计算，不因用户角色授权而被绕过。 |
| `sys_permission` | 全局权限目录 | 平台维护；租户使用经套餐和角色共同确认的权限。 |
| `sys_config` | 全局配置 | 平台维护；租户配置如有需求，应单独设计租户归属，不直接复用这张表。 |
| `sys_role` | 平台与租户混合 | `tenant_id IS NULL` 为平台角色，非空为所属租户角色；查询和写入必须分别处理，不能套用单一租户过滤。 |
| `sys_user_tenant` | 租户成员关系 | 租户管理按当前租户访问；认证服务按用户查询其所有有效租户属于受控内部读取。 |
| `sys_user_role` | 租户与平台角色绑定 | 本阶段确定：租户角色绑定保存实际 `tenant_id`，平台角色绑定使用 `tenant_id IS NULL`。当前字段不允许空；阶段 1 必须新增迁移并修正查询，拒绝以某个真实租户冒充平台授权。 |
| `sys_role_permission` | 租户角色权限关系 | 按角色及同租户校验；平台角色的功能权限规则在阶段 1 单独处理。 |
| `sys_role_dept` | 租户角色部门范围 | 角色、部门、关系三者必须属于同一租户。 |
| `sys_user_post` | 租户用户岗位关系 | 用户必须是本租户有效成员，岗位必须属于本租户。 |
| `sys_dept` | 租户组织数据 | 按当前租户访问；后续再叠加本次操作的数据范围。 |
| `sys_post` | 租户组织数据 | 按当前租户访问；若参与部门数据范围，先补齐岗位与部门的明确关联。 |

## 平台与租户操作规则

1. **普通租户接口：** 必须有有效 `currentTenantId`。读写目标和相关外键均属于当前租户；缺少租户上下文时拒绝，不通过省略租户条件退化为全表访问。
2. **平台接口：** 仅平台授权角色可调用。跨租户操作必须由具体平台服务显式处理，不能因为超级管理员拥有功能权限通配符，就让普通租户 Mapper 自动跨租户读取。
3. **租户切换：** 只能切到当前用户可访问的有效租户；切换后重新计算角色、功能权限和部门归属。等待用户选择租户的状态不允许调用租户业务接口。
4. **内部认证读取：** 登录与 `userInfo` 需要读取全局用户、有效租户和角色。这类跨租户读取应限定在认证服务，不能作为通用 Mapper 绕过入口暴露给业务 API。
5. **状态校验：** 用户禁用、租户停用或到期、成员失效、角色或权限停用不得继续产生有效授权。当前 `sys_user_tenant` 尚无成员状态字段，阶段 1 再通过新迁移和服务规则补齐。
6. **数据权限：** 功能权限确定“能做什么”，数据权限确定“对哪些记录做”。只有授予本次操作权限的角色可以参与本次数据范围计算；具体规则按任务计划阶段 2 和阶段 4 实现。

## 初始管理员与开发验收数据

`V1__baseline.sql` 只初始化系统配置，没有管理员账号、角色或权限数据。当前 `sys_role.tenant_id` 可为空，`sys_user_role.tenant_id` 不可为空；这一不对称意味着平台角色绑定还没有完整的数据库表示。本阶段确定以 `NULL tenant_id` 表示平台绑定，阶段 1 用新迁移修改字段约束，并将用户与角色的唯一性约束调整为适合这一模型的规则。迁移前要核查历史数据中同一用户重复绑定同一角色的情况，修正角色查询必须同时匹配角色和绑定的作用域。完成作用域迁移后才建立初始管理员；不写入伪造的租户 ID，也不通过公开初始化接口创建管理员。

管理员建立方式现由 `V5__initialize_admin.sql` 落实：在 `V3` 完成平台绑定结构迁移后，仅当 `admin` 不存在时创建全局用户、`tenant_id IS NULL` 的平台 `superadmin` 角色及绑定。初始密码为 `admin123...`（包含三个英文句点），迁移只保存 BCrypt 哈希；已有 `admin` 的密码和授权不会被覆盖。生产部署后应更换初始密码，详情见[阶段 1 初始化说明](阶段1-RBAC初始化与验收.md)。

阶段 1 的开发验收数据至少包含以下组合；这些是数据准备规格，尚未向任何数据库写入：

| 身份与数据 | 用途 |
| --- | --- |
| 1 名平台管理员 | 核对平台接口、租户选择及平台角色边界。 |
| 租户 A、租户 B，各有不同套餐 | 核对租户隔离、套餐权限上限。 |
| 1 名同时属于 A、B 的普通用户 | 核对相同账号切换租户后角色与权限独立。 |
| 1 名仅属于 A 的普通用户 | 核对无法进入 B。 |
| 每个租户至少 2 个范围不同的角色 | 核对角色分配及后续按操作计算的数据范围。 |
| 1 个仅由角色授予、未被套餐包含的权限码 | 核对套餐与角色权限取交集。 |
