# 阶段 2：组织归属与数据范围规则

## 当前实现边界

`sys_user` 是跨租户账号；一个账号在一个租户内最多一个主部门，保存在 `sys_user_tenant.dept_id`。`sys_post.dept_id` 表示岗位所属部门，不反推成员的主部门。V6 迁移将历史成员和岗位的归属保持为空，因为现有关系无法可靠推断。空部门不是根部门，也不是全租户权限。

当前租户必须有效。部门、成员、角色、自定义部门绑定都必须属于同一租户。部门树暂不开放移动和删除；创建时沿实际父子关系计算 `ancestors`，使用归属时验证整条祖先链，停用前检查有效子部门、成员、岗位及自定义角色范围。成员部门变更和角色范围变更在事务提交后撤销受影响用户的旧会话。`userInfo.deptId` 每次按当前租户的有效成员和有效部门重算。

## 本次操作使用哪些角色

数据范围的输入是**具体权限码**，例如 `system:post:list`，而不是登录者持有的全部角色。`SysRoleMapper.selectAuthorizedDataScopeRoles` 只返回：已启用账号在当前有效租户中的有效成员关系、有效租户角色、该角色实际绑定的有效权限码，以及当前有效套餐确实允许的权限。平台角色和租户伪装 `superadmin` 角色不参与。结果为空时，受数据范围保护的操作拒绝；平台超级管理员的功能权限通配符不自动产生租户数据范围。

两个角色分别授予 `system:post:list` 和 `system:post:update` 时，列表只用前者的范围，修改只用后者的范围。角色 A 授予列表且范围为本部门，角色 B 为全部但未授予列表，列表仍只可看本部门。角色 B 的“全部”不能放大角色 A 的授权。

## 六种范围

范围均以**当前租户**为外层硬边界，不能跨租户。部门 ID 必须来自当前租户的有效部门；子部门只沿有效的父子链展开。

| 值 | 名称 | 允许条件 |
| --- | --- | --- |
| 1 | 全部 | 当前租户内该动作对应的全部目标 |
| 2 | 自定义部门 | 目标部门等于角色选择的有效部门之一；不自动包含子部门 |
| 3 | 本部门 | 目标部门等于当前成员主部门 |
| 4 | 本部门及以下 | 目标部门等于主部门或其有效子部门 |
| 5 | 仅本人 | 目标的明确本人字段等于当前账号 ID |
| 6 | 部门及以下或本人 | 满足第 4 项或第 5 项 |

本部门为空时，3 和 4 返回空范围；6 只保留本人分支。自定义部门集合为空、部门停用或绑定失效时返回空范围。本人字段若为空也不匹配；不能用 `update_by` 或部门负责人字段代替。

以当前用户 10、当前租户 A、主部门 100、有效子部门 101/102、另一个租户的部门 900 为例，六种范围依次得到：

| 范围 | 输出示例 |
| --- | --- |
| 1 | `all=true`，仍限定租户 A |
| 2 | 若角色选择 102，则 `deptIds={102}`；900 不能写入绑定 |
| 3 | `deptIds={100}` |
| 4 | `deptIds={100,101,102}` |
| 5 | `self=true,userId=10`，只比较目标 `create_by` |
| 6 | `deptIds={100,101,102},self=true,userId=10` |

当前实现的 `resolveCurrentTenantDataScope(permissionCode)` 返回 `tenantId/userId/all/self/deptIds`，或在没有有效授权分支时抛出拒绝异常。它只计算业务范围，不自行拼接 SQL，也不会被持久化模块反向调用。

## 多角色与拒绝规则

列表、详情和导出：只将**授予对应动作权限**的角色范围取并集，再与当前租户条件取交集。角色范围 1 在该租户内吸收其他范围。未登录、无当前租户、租户或成员失效、权限码缺失、没有授权角色、部门范围为空均不能放宽条件。后台任务没有请求上下文时不得直接执行受保护的租户查询；未来如需任务访问，必须显式建立任务身份及租户并经同一策略验证。

修改、删除、状态变更和关系分配：分别使用对应动作的权限码查角色，先按 ID 读取目标的租户和归属，再判断其是否落在本动作的范围内；批量操作逐一覆盖全部目标，存在一个越权目标就整体拒绝。只给查询加条件不足以保护写操作。创建操作由服务端写入 `tenant_id` 与 `create_by`，客户端给出的部门必须属于当前租户且落在创建动作授权范围内。受控平台操作另设明确入口与权限，不从超级管理员角色推断跨租户读写豁免。

## 首个受保护资源的决策表：`sys_post`

`sys_post` 是租户业务资源，字段为 `tenant_id`、`dept_id`、`create_by`。它比全局账号表 `sys_user` 更适合作为阶段 4 的首个落地对象。岗位业务 API 已按下表接入租户和数据范围条件，并通过首轮动态验收；其他业务资源仍需各自审查。

| 动作 | 权限码 | 目标字段 | 允许条件 | 拒绝结果 |
| --- | --- | --- | --- | --- |
| 列表/详情 | `system:post:list` / `system:post:detail` | `tenant_id, dept_id, create_by` | 当前租户 + 对应读权限角色的范围并集；分页总数同条件 | 查询不到越权行；无上下文直接 403 |
| 创建 | `system:post:create` | 服务端设置 `tenant_id, create_by`；请求 `dept_id` | 部门属于当前租户且在创建权限角色的部门范围内；仅本人范围只允许归入本人主部门或不归属部门 | 403，整笔写入不发生 |
| 修改/停用 | `system:post:update` / `system:post:status` | 原目标 `tenant_id, dept_id, create_by`；新 `dept_id` | 原目标在本动作角色范围内；新部门也在本动作范围内 | 403，原记录不变 |
| 删除 | `system:post:delete` | 原目标 `tenant_id, dept_id, create_by` | 原目标在删除权限角色范围内 | 403，原记录不变 |
| 岗位成员关联 | `system:post:member:list` / `system:post:member:assign` | 岗位与成员的 `tenant_id` | 岗位在本动作范围内，成员属于同一租户且有效；不能借关联改变成员主部门 | 403，关系不变 |

所有动作先检查目标租户。即使某个角色的范围值为 1，也只能覆盖本动作、当前租户的岗位。对于历史 `dept_id` 为空的岗位，部门条件不匹配，只有全部或 `create_by` 符合的本人分支可能匹配。阶段 4 写 SQL 前要对表别名、分页总数、详情、批量写入、逻辑删除和联表场景逐项验收。

## 对照参考项目后的取舍

RuoYi-Vue-Plus 把功能权限对应角色、数据范围计算、SQL 拦截和写目标校验分成不同环节，这些边界有参考价值。Whim 保留自己的全局账号加租户成员模型，先在角色服务中取得实际授权角色；阶段 4 再把业务计算结果交给持久化执行层。不会搬用参考项目的注解、SpEL SQL 模板、线程局部变量或其模块依赖方式。

## 本次验收状态

源码、迁移、Mapper XML 和接口文档已更新；XML 结构和 `git diff --check` 已通过。使用本地 MySQL 测试库事务插入临时数据，直接执行源码中的三个查询并回滚，已验证：有效子部门排除停用、软删及其他租户；自定义部门排除停用及跨租户绑定；无授权用户返回空角色；本次权限不被无权限的全量角色放大；两租户角色独立；套餐撤权后无可用角色。V6 的四条 SQL 还在克隆表的临时数据库中完整执行，验证了两列、历史错误绑定停用和六个功能权限码；临时数据库已清理。

后续已使用 JDK 25 重新打包并启动本地服务，实际数据库 Flyway 历史已到 V8。岗位样本的部门子树与本人并集、按动作授权角色取范围、跨租户拒绝及授权撤销已通过真实 HTTP 请求和数据库核对；详见[阶段 4 动态验收](阶段4-岗位数据权限落地记录.md)。这些结果只证明岗位样本，不能代替其他业务资源、联表或后台任务的验收。

随后补齐六种范围的应用级矩阵：两租户临时数据覆盖六种范围的分页总数、详情、创建、修改、状态变更和删除，另核对空主部门、自定义部门停用、无本次权限的全量角色和两个令牌的租户上下文，**168 项全部通过**，见[范围矩阵明细](阶段2-六种数据范围动态验收明细.json)。部门、角色数据范围及成员主部门管理接口另有 **38 项检查全部通过**，见[组织接口明细](阶段2-组织管理接口动态验收明细.json)。临时数据均已清理。

组织接口验收发现清除成员主部门时，实体更新会跳过 `null`，导致接口虽返回成功却未清除数据库字段。现改用显式更新条件写入 `NULL`，重新打包启动并复测，旧令牌在事务提交后失效、重新登录后 `deptId` 为空。阶段 2 在当前组织模型与岗位样本范围内完成验收；其他业务资源的数据权限仍属阶段 4。
